# AIAssistantService

ИИ-ассистент платформы **Tapik** — генерирует подсказки для ответа в чате на основе LLM (Groq или локальная Ollama) и умеет ставить сообщения на отложенную отправку. Часть микросервисной архитектуры Tapik.

## Роль в системе

```
                     ┌──────────────────┐
   HTTP (JWT) ──────▶│ AIAssistantService│
                     └─────────┬─────────┘
                               │ gRPC (x-internal-key)
                               ▼
                        ┌─────────────┐
                        │ ChatService │
                        └─────────────┘
```

- Принимает HTTP-запросы от авторизованных пользователей (через `JwtAuthGuard`, тот же `JWT_SECRET`, что у AuthService).
- Обращается к внешним LLM-провайдерам (Groq API или self-hosted Ollama) для генерации текста.
- Периодически (каждые 30 секунд) проверяет БД на отложенные сообщения и отправляет их в ChatService по внутреннему gRPC, защищённому shared-secret заголовком `x-internal-key`.
- Слушает `message.sent` от ChatService (очередь `ai_assistant_events`) и, если у получателя включён авто-ответ и он офлайн, генерирует и отправляет ответ от его имени.
- При подозрении на срочность (по пожеланиям пользователя) публикует `urgent.notify` в NotificationService.

## Технологии

- **NestJS 11** (TypeScript), гибридное приложение (HTTP + `@nestjs/schedule` cron)
- **PostgreSQL** через **Prisma 7** (`@prisma/adapter-pg`)
- **Redis** (ioredis) — кэш контекста собеседника
- **gRPC** (`@grpc/grpc-js`) — клиент к ChatService (`ChatInternal`)
- **Groq SDK** и raw HTTP (`@nestjs/axios`) — LLM-провайдеры
- **class-validator / class-transformer** — валидация DTO
- Path-алиасы: `@common/*`, `@modules/*`, `@proto/*`

## Возможности

- `POST /assistant/suggest-replies` — по истории переписки возвращает 3 варианта ответа на языке последнего сообщения (поддержка русского, английского, армянского в двух алфавитах, включая армянский латиницей), с учётом тона (`casual` / `formal` / `friendly`).
- Отложенная отправка сообщений: пользователь планирует сообщение на будущее время, фоновый раннер сам отправляет его в нужный момент через ChatService. Завершённые записи (`sent`/`failed`/`cancelled`) старше 30 дней вычищаются суточным кроном — таблица не растёт бесконечно.
- Авто-ответ: пока пользователь недоступен (нет активного WebSocket-сокета), сервис отвечает собеседнику от его имени, подстраиваясь под язык, стиль и (если задано) пожелания пользователя — см. раздел «Авто-ответ» ниже.
- Абстракция над LLM-провайдерами (`ModelProvider`) — переключение Groq ↔ Ollama одной переменной окружения, без изменения кода вызывающей стороны. Сетевые/временные сбои провайдера ретраятся (до 3 попыток, растущая пауза) прежде чем сдаться.

## API

Все эндпоинты защищены `JwtAuthGuard`, кроме `GET /` (исключение | `GET /assistant/digest`).

| Метод    | Путь                            | Rate limit | Описание                                                                |
| -------- | ------------------------------- | ---------- | ----------------------------------------------------------------------- |
| `POST`   | `/assistant/suggest-replies`    | 10/мин     | Сгенерировать 3 варианта ответа по истории сообщений                    |
| `POST`   | `/assistant/schedule`           | —          | Запланировать отложенную отправку сообщения в чат                       |
| `GET`    | `/assistant/schedule`           | —          | Список ожидающих отправки сообщений текущего пользователя               |
| `GET`    | `/assistant/digest`             | 10/мин     | Дайджест непрочитанных сообщений по всем чатам (кэш 120с в Redis)       |
| `DELETE` | `/assistant/schedule/:id`       | —          | Отменить запланированное сообщение                                      |
| `POST`   | `/assistant/auto-reply/:chatId` | 20/мин     | Включить/выключить авто-ответ для чата, опционально задать пожелания (`customInstructions`) |
| `GET`    | `/assistant/auto-reply/:chatId` | —          | Текущее состояние тумблера и `customInstructions` для чата              |

### `POST /assistant/suggest-replies`

```json
{
  "messages": [{ "role": "other", "content": "Привет! Как дела?" }],
  "tone": "casual",
  "chatId": "uuid",
  "participantName": "Аня"
}
```

→ `["Привет! Отлично, а у тебя?", "Привет! Занят немного, но норм", "Привет, всё хорошо!"]`

### `POST /assistant/schedule`

```json
{ "chatId": "uuid", "content": "Напоминание", "sendAt": "2026-09-08T10:00:00Z" }
```

### `POST /assistant/auto-reply/:chatId`

```json
{ "enabled": true, "customInstructions": "Отвечай от имени моего администратора. Если дело очень срочное — предупреди меня." }
```

`customInstructions` опционален (до 1000 символов), пустая строка/отсутствие поля сбрасывает пожелания. Подставляется в системный промпт отдельным приоритетным блоком — влияет на тон/персону/содержание, но не отменяет базовые правила языка.

## Авто-ответ

Пока пользователь недоступен (нет активного сокета в `user_sockets:{userId}`), сервис может отвечать за него по факту входящего сообщения.

**Контекст для генерации:**
- последние настоящие (не авто-ответные) сообщения пользователя в этом чате — образец стиля/языка/длины (`GetUserMessagesInChat`);
- последняя переписка в чате целиком, хронологически, включая собственные прошлые авто-ответы (`GetRecentMessages`) — чтобы не здороваться заново и не повторять уже сказанное;
- `customInstructions` пользователя для этого чата, если заданы.

**Персона:** по умолчанию отвечает как сам пользователь, копируя его манеру речи. Если `customInstructions` просят другую роль (например «отвечай от имени администратора») — использует эту роль вместо личного стиля пользователя.

**Групповые чаты:** в чатах с 3–5 участниками модель получает имена всех участников (`UserInternal.GetProfiles`) и явно решает, адресовано ли сообщение отсутствующему пользователю, — если нет, не отвечает. В группах больше 5 участников авто-ответ не срабатывает вовсе.

**Срочные уведомления:** если по `customInstructions` и смыслу входящего сообщения похоже, что дело срочное (настойчивость, явная просьба предупредить), в NotificationService публикуется `urgent.notify` — push уходит на все устройства пользователя независимо от online-статуса.

**Ограничения расхода:**
- дневной бюджет — не более 100 сгенерированных авто-ответов на пользователя в сутки;
- burst-лимит — не более 3 авто-ответов на один чат за 10 минут; при превышении сервис один раз шлёт статичное (без обращения к LLM) уведомление «отвечу позже» и молчит до сброса окна;
- явные реплики-закрытия («спасибо», «ок», «понял» и т.п.) не доходят до LLM вообще;
- явная провокация/агрессия без вопроса или дословный повтор уже отвеченного — модель может решить не отвечать текстом (`reply: null`), не тратя лимит на бессмысленную перепалку.

**Не начинает одно и то же слово-паразит** (например всегда "норм") в каждом ответе — база данных ловит и не пускает в примеры стиля свои же прошлые авто-ответы, разрывая петлю самоподражания.

## gRPC: клиенты к ChatService и UserService

`chat.proto` (`ChatInternal`, ChatService): `SendMessageInternal`, `IsMember`, `GetUserMessagesInChat`, `GetRecentMessages`. Каждый вызов несёт метаданные `x-internal-key: <INTERNAL_API_KEY>` — ChatService отклонит запрос без корректного ключа (`InternalGrpcAuthGuard`, сравнение константного времени).

`user.proto` (`UserInternal`, UserService): `GetProfiles` — резолвинг `username`/`avatarUrl` для дайджеста непрочитанных и для имён участников в групповом авто-ответе.

Планировщик (`ScheduleRunnerService`, `@Cron(EVERY_30_SECONDS)`):

1. Берёт из БД до 50 сообщений со статусом `pending` и `sendAt <= now()`.
2. Захватывает Redis-блокировку (`SET NX PX 25000`) — при горизонтальном масштабировании только один инстанс обрабатывает тик, сообщения не дублируются.
3. Для каждого сообщения повторно проверяет членство отправителя в чате (`IsMember`) — если пользователя успели удалить из чата, сообщение помечается `failed`, а не отправляется.
4. Отправляет через `SendMessageInternal`, обновляет статус (`sent` / `failed`). Ошибка одного сообщения не прерывает обработку остальных в батче.

Тот же сервис держит второй крон, `purgeTerminalMessages` (`@Cron(EVERY_DAY_AT_4AM)`, своя Redis-блокировка): удаляет записи `ScheduledMessage` в статусах `sent`/`failed`/`cancelled` старше 30 дней.

## Переменные окружения

| Переменная                  | Обязательна                   | Назначение                                                                                                 |
| --------------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `PORT`                      | нет (3007)                    | HTTP-порт                                                                                                  |
| `JWT_SECRET`                | да                            | Секрет для проверки access-токенов (общий с AuthService)                                                   |
| `AI_PROVIDER`               | нет (`groq`)                  | `groq` или `ollama`                                                                                        |
| `GROQ_API_KEY`              | да, если `AI_PROVIDER=groq`   | Ключ Groq API                                                                                              |
| `GROQ_MODEL`                | нет                           | Модель Groq (по умолчанию `qwen/qwen3.8-27b`)                                                              |
| `OLLAMA_URL`                | да, если `AI_PROVIDER=ollama` | URL self-hosted Ollama                                                                                     |
| `OLLAMA_MODEL`              | да, если `AI_PROVIDER=ollama` | Имя модели в Ollama                                                                                        |
| `REDIS_HOST` / `REDIS_PORT` | нет                           | Redis для кэша контекста                                                                                   |
| `DATABASE_URL`              | да                            | Строка подключения PostgreSQL                                                                              |
| `CHAT_SERVICE_GRPC_URL`     | да                            | Адрес gRPC-сервера ChatService                                                                             |
| `INTERNAL_API_KEY`          | да                            | Shared-secret для внутренних gRPC-вызовов (тот же ключ, что у ChatService/MediaService/ReactionsService)   |
| `USER_SERVICE_GRPC_URL`     | да                            | Адрес gRPC-сервера UserService (`UserInternal.GetProfiles`)                                                |
| `RABBITMQ_URL`              | да                            | AMQP-подключение, очередь `ai_assistant_events` (потребляет `message.sent` от ChatService для авто-ответа) |

## Безопасность

- Все пользовательские эндпоинты требуют валидный JWT (`Authorization: Bearer`).
- Глобальный `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true })` — лишние/некорректные поля отклоняются.
- Длина контента в истории сообщений ограничена (`@MaxLength(4000)`) для защиты от prompt injection и чрезмерных затрат на LLM.
- Таймаут (`timeoutMs`) на каждый вызов LLM-провайдера — зависший провайдер не блокирует запрос навсегда.
- Сетевые сбои вызова LLM (обрыв связи, таймаут, 429/5xx) ретраятся с растущей паузой (до 3 попыток); ошибки самой модели (неверный промпт, авторизация) — нет, повтор там бессмысленен.
- Исходящие gRPC-вызовы к ChatService и UserService подписаны shared-secret заголовком, не полагаются только на сетевую изоляцию.
- Авто-ответ ограничен дневным бюджетом и burst-лимитом на чат — защита от неограниченного счёта за LLM при спаме/провокациях от собеседника.
